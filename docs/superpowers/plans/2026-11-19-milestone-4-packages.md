# Milestone 4: packages and autostart docs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The implementer step runs through the `local-implementer` skill.

**Goal:** every platform in spec section 4 gets an installable artifact that a clean machine can install, run and remove: `.deb` and `.rpm` for arm64 and x86-64 (Raspberry Pi OS 64-bit included), a Windows `.zip` for x86-64 and arm64, a universal macOS `.tar.gz`, each with man pages, shell completions, `LICENSE`/`NOTICE` and the docs; plus `docs/autostart.md`, which shows how to run `serve` under systemd, launchd or Windows Task Scheduler, every one of them opt-in. The milestone ends with a release.

**Architecture:** no new crate and no runtime behaviour change. The binary gains one hidden subcommand, `generate-assets <DIR>`, that writes man pages (clap_mangen) and completions (clap_complete) from the real `Cli`, so they can never drift from the flags. Packaging is shell scripts under `dev/` (Linux: `cargo-deb` and `cargo-generate-rpm`, the same tools and pins as `../terminal`; macOS and Windows: archive scripts lifted out of the workflow), metadata in `crates/featherbittorrent/Cargo.toml`, and service examples under `packaging/` that are shipped as documentation only. Every artifact is smoke-tested by a shared CLI smoke script (`dev/smoke-cli.sh` and its PowerShell twin) inside clean containers or runners before anything is published.

**Tech Stack:** as milestone 2, plus `clap_complete` and `clap_mangen` (workspace dependencies), `cargo-deb@3.8.0` and `cargo-generate-rpm@0.21.1` (CI tools, not dependencies), `almalinux:9` as the Linux build image, GitHub Actions containers `debian:12`, `debian:13`, `ubuntu:22.04`, `fedora:41`, `rockylinux:9` for smoke tests.

**Spec:** `docs/superpowers/specs/2026-11-14-featherbittorrent-design.md` (section 4 platforms and distribution, the non-goal "Autostart" in section 3, section 6.1 running, section 8 release standards).

**Prior art to copy from:** `../terminal/dev/package-linux.sh`, `../terminal/dev/smoke-linux.sh`, `[package.metadata.deb]` and `[package.metadata.generate-rpm]` in `../terminal/crates/fbterm/Cargo.toml`, and the `linux` and `linux-smoke` jobs in `../terminal/.github/workflows/release.yml`. featherbittorrent is a CLI/TUI: no desktop entry, no icons, no X11/Wayland/Vulkan libraries; drop all of that rather than adapting it.

## Builder's calls made in this plan

Each is a call the spec leaves open (section 4 and section 9 "Packaging tools"); each can be revisited by whoever executes the plan, with the owner told.

1. **Windows: `.zip`, no MSI.** [builder's call] A CLI and headless server needs no Start menu entry, no admin rights to install and no uninstaller; a zip is what the 0.1.0 release already ships, and an installer is the one place that would be tempted to register a service, which the owner ruled out.
2. **macOS: universal `.tar.gz`, no `.dmg`.** [builder's call] A `.dmg` is a drag-to-Applications GUI convention; a terminal program goes on `PATH`, and the 0.1.0 archive layout already works. No notarization in this milestone (no Apple Developer identity in the repo); the docs say how to clear the quarantine attribute a browser download gets.
3. **Linux build image `almalinux:9` (glibc 2.34) instead of `debian:12` (2.36).** [builder's call] One binary in the `.deb`, the `.rpm` and the `.tar.gz`; 2.34 is RHEL 9's glibc, the oldest of the supported systems, so the `.rpm` installs on Rocky/Alma 9 and the `.deb` on Ubuntu 22.04. Raspberry Pi OS 12 and 13 (2.36, 2.41) are above it. Raspberry Pi OS 11 (bullseye, 2.31) is not supported, as it already was not with 0.1.0. The packaging script refuses a binary that needs a glibc symbol newer than `GLIBC_2.34`, as in `../terminal`.
4. **glibc, not static musl.** [builder's call] musl's allocator is markedly slower under a torrent engine's allocation pattern, and the Pi 2B is the low end; glibc 2.34 is old enough for every target.
5. **Hand-written package dependencies, guarded by a `NEEDED` allow list.** [builder's call] The binary links only `libc.so.6`, `libm.so.6`, `libgcc_s.so.1` and the dynamic loader (ring and rustls are static, keyring's Linux store is pure-Rust D-Bus). The `.deb` declares `libc6 (>= 2.34), libgcc-s1`; the `.rpm` uses cargo-generate-rpm's automatic requirements. `dev/check-linux-binary.sh` fails the build if a new shared library ever appears, so the declared dependencies cannot silently become wrong.
6. **Man pages and completions are generated, by a hidden `generate-assets <DIR>` subcommand.** [builder's call] Generating from the real `clap::Command` means they never disagree with `--help`; a hidden subcommand (present in release builds, absent from help and completions) is the only way to reach the `Cli` type, which lives in a binary crate. Pages: `featherbittorrent.1` plus one per subcommand (`featherbittorrent-serve.1`, `featherbittorrent-user.1`, `featherbittorrent-user-set.1`, ...). Completions for bash, zsh, fish and PowerShell.
7. **No maintainer scripts at all** (no `postinst`, `prerm`, `%post`, ...). [builder's call] Nothing to enable, nothing to stop, no system user created: the owner's non-goal says packages never install or enable a service, and a package that creates a service user is halfway there. Creating the user is one documented command in `docs/autostart.md`.
8. **Service examples are documentation**, installed under `/usr/share/doc/featherbittorrent/examples/` (deb and rpm) and `examples/` in the archives; never under `/lib/systemd`, `/usr/lib/systemd` or `/etc`. [owner non-goal, placement is the builder's call]
9. **System service paths: `FBTT_CONFIG_DIR=/var/lib/featherbittorrent/config`, `FBTT_DATA_DIR=/var/lib/featherbittorrent/library`, run as a static system user `featherbittorrent`.** [builder's call] The same split the `Dockerfile` already uses under `/data`; `/var/lib` because the server rewrites `config.yaml` itself (devices added from a TUI), which `/etc` is the wrong place for. A static uid (not `DynamicUser=`) because a NAS mount needs a stable owner. This promotes `FBTT_CONFIG_DIR`/`FBTT_DATA_DIR` from "debug knobs" to supported settings for services and containers (the Dockerfile already relies on them); docs and `CLAUDE.md` say so. User services (systemd `--user`, launchd agent) keep the platform defaults, so the TUI on the same machine shares the library and gets the lock hand-off.
10. **Windows autostart is Task Scheduler, not `sc.exe`.** [builder's call] `featherbittorrent.exe` does not speak the service control protocol, so `sc.exe create` registers a service that fails to start (error 1053). A native Windows service mode is a future code change, out of scope here. The docs name a service wrapper (WinSW) as the alternative and say plainly that stopping a scheduled task kills the process: the last save is the five-minute periodic one.
11. **Artifact names.** [builder's call] Archives keep their 0.1.0 names (`featherbittorrent-<version>-<target>.tar.gz|zip`) so existing download scripts keep working; packages follow `../terminal`: `featherbittorrent-<version>-linux-<arch>.deb|rpm` with `<arch>` `x86_64` or `aarch64`. Every artifact gets a `<file>.sha256` beside it.
12. **Smoke images.** [builder's call] `debian:12` and `debian:13` stand in for Raspberry Pi OS 12 and 13 (same userland; Raspberry Pi publishes no container image), `ubuntu:22.04` for the oldest `.deb` glibc, `fedora:41` and `rockylinux:9` for `.rpm`, `ubuntu:22.04` for the `.tar.gz`. Each on x86_64 and aarch64 native runners.
13. **Smoke content.** [builder's call] A release binary has no `--offline` and no `--stop-file`, and `serve` without them would join the public DHT, so no smoke runs `serve`. The release-safe smoke is: `--version`, `--help`, `serve --help`, `serve --offline` refused with exit 2 (which also proves the artifact is a release build), and `user set` with a piped password then `user list` on a scratch home, which exercises path resolution, the library lock, config writing and Argon2. After removal the scratch config must still be there.

Upgrading the package does not restart anything: `sudo systemctl restart featherbittorrent` after an upgrade.
    3. **systemd, user service** (a desktop or laptop): copy the user unit to `~/.config/systemd/user/`, `systemctl --user daemon-reload`, `systemctl --user enable --now featherbittorrent`, `loginctl enable-linger "$USER"` to keep it running without a login session; the TUI on the same machine sees the library held and offers to connect to it (`docs/server.md`, the hand-off).

Remote access goes through a reverse proxy (`docs/reverse-proxy.md`). Network filesystems: sparse files may be absent and moves may cross devices, which the engine handles; the NAS must be writable by the service's uid.
    5. **launchd** (macOS): install the binary to `/usr/local/bin` from the archive; copy the plist to `~/Library/LaunchAgents/`, replace `/Users/YOU` (`sed -i '' "s|/Users/YOU|$HOME|" ...`); `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/io.featherbit.featherbittorrent.plist`; stop with `launchctl bootout gui/$(id -u)/io.featherbit.featherbittorrent` (SIGTERM, then the last save, 90 s grace). A LaunchDaemon (`/Library/LaunchDaemons`, a `UserName` key, `FBTT_*` in `EnvironmentVariables`) for a machine with nobody logged in, with the note that a daemon cannot reach the login keychain (irrelevant to `serve`, which keeps only hashes).

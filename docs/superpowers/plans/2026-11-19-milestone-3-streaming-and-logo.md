# Milestone 3: streaming to mpv/VLC and the image logo, release 0.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The implementer step runs through the `local-implementer` skill.

**Goal:** `s` opens the selected file in mpv or VLC on the TUI's machine, from the local engine or from a server, while it downloads; the real featherbit mark is drawn as a crisp image in the header and on the help screen in terminals that speak kitty graphics, iTerm2 inline images or sixel, and the text title stays everywhere else; featherbittorrent ships `0.2.0`.

**Architecture:** the TUI's `s` sends `Command::Stream`; each backend answers with `Notice::Play(PlayTarget)`: a file path, or a stream URL. The local backend hands a path when the torrent is seeding, otherwise it starts (on demand) a loopback `fbt_api::ApiServer` over its own session whose authenticator only lets through `GET`/`HEAD` on the file-stream route with a short-lived token scoped to that one file. The server issues the same kind of token from a new route, `POST /api/v1/stream-tokens`, and the remote backend turns it into a URL on the server; when a gateway in front of the server needs its own credentials (which a player cannot send), the TUI relays that same server URL through a loopback relay that adds the gateway's header. The binary launches the player with a playlist file, never with the URL, so no token reaches a process listing. The logo lives in `fbtt-tui::graphics` (pure: capability parsing, image preparation, the three encoders, placement bookkeeping) plus a probe in the binary that queries the terminal once, before the event loop, with a 300 ms timeout.

**Tech Stack:** as milestone 2, plus fbt-lib `v0.10.0` (`fbt`, `fbt-api`; Task 0), tokio `process`, `png` (decode the mark, encode for iTerm2), `color_quant` (sixel palette), `rustix` (Unix only: `poll` and `read` on the tty for the probe; already in the tree through crossterm).

**Spec:** `docs/superpowers/specs/2026-11-14-featherbittorrent-design.md` (goal 5, sections 3, 5.2, 5.3, 5.4 and 9 matter most).

## What fbt-lib v0.9.0 already gives us (read at tag `v0.9.0`)

- **Reads that wait and prioritise:** `fbt::TorrentHandle::open_file(index) -> Result<fbt::FileReader, SessionError>` (`crates/fbt-session/src/torrent/mod.rs`); `FileReader` is `AsyncRead + AsyncSeek`, a read of a missing piece waits, and its position sets piece deadlines over a `ReadAhead` window (`crates/fbt-session/src/stream/{mod.rs,reader.rs}`). At most 16 readers per torrent (`SessionError::TooManyReaders`).
- **The HTTP stream route:** `GET`/`HEAD /api/v1/torrents/{id}/files/{index}/stream` (`crates/fbt-api/src/routes/stream.rs`): one `bytes` range (`200`, `206` with `Content-Range`, `416`), multi-range or malformed ranges served whole, `Content-Type` from the extension, `X-Content-Type-Options: nosniff`, 64 KiB chunks, a permit from `ApiConfig::max_streams` (`503 too_many_streams`), bodies end on shutdown, and `ApiServer` ends a stalled connection after `ApiConfig::stream_idle_timeout` (600 s). The range parser is `fbt_api::range::parse_range` (public, `#[doc(hidden)]`); we never call it ourselves.
- **Auth on that route:** under `Auth::Custom`, every request reaches `fbt_api::Authenticator::authorize(&AuthRequest)`. `AuthRequest` carries `method`, `matched_path` (the route *template*), `headers`, `query_token` (the decoded `?token=`, offered only on the two stream routes and `GET /api/v1/events`, at most 4096 bytes) and `peer` (`crates/fbt-api/src/auth.rs`).
- **The gap:** `AuthRequest` does not carry the request's actual path, so an authenticator cannot tell `/torrents/A/files/0/stream` from `/torrents/B/files/7/stream`. A token can be limited to "the stream routes" but not to one file. Task 0 adds the path in fbt-lib `v0.10.0`. Nothing else is missing: no other fbt-lib change is planned.

## Decisions (builder's calls)

Each is marked here once; the tasks implement them.

1. **The remote player URL is the server's own stream route with a stream token** (honours spec 5.4 [owner]): `POST /api/v1/stream-tokens` returns `/api/v1/torrents/<id>/files/<index>/stream?token=<t>`. [builder's call] Why: it reuses fbt-api's tested range streaming and its stall guard instead of a second implementation.
2. **Stream tokens:** 32 random bytes, base64url without padding; stored as SHA-256 only; scoped to one exact path; must be first used within 60 s of issue; then valid until 30 minutes pass without a request, and never beyond 8 hours after issue; at most 64 live per server (16 in a local endpoint), oldest evicted. They are independent of the TUI's session, so quitting a remote TUI does not stop a film. [builder's call] Why: a player re-requests the URL on every seek, so single-use cannot work; the 60 s first-use window makes an unused URL die fast, and the idle limit survives a paused film.
3. **The player never gets a URL on its command line:** the binary writes an M3U playlist (`0600`, in `<data_dir>/play/`, random name, created with `create_new`) and passes its path; the file is deleted when the player exits or 30 s after launch, whichever comes first; files older than 12 h in that folder are swept at start. A complete local file is passed as its absolute path (no secret). [builder's call] Why: the token is a credential while it lives, and argv is world-readable on Linux and macOS (`ps`); a playlist path is not.
4. **Local file versus loopback URL** (spec section 9): a path when the torrent is `TorrentState::Seeding` (every wanted piece verified *and on disk*), the file's priority is not `Skip`, its `downloaded == len`, and the file exists on disk with that length (checked on the blocking pool); otherwise a loopback stream URL. [builder's call] Why: `Seeding` is the only state fbt-lib documents as "on disk"; a verified piece can still sit in the write cache, and a skipped file can live in the part file, both of which the stream route reads correctly and a path would not.
5. **The local endpoint is fbt-api itself:** `fbt_api::ApiServer::start(session.clone(), config)` on `127.0.0.1:0` with `Auth::Custom(LocalStreamAuth)`, started on the first `s` and shut down before the engine. `LocalStreamAuth` answers `403` to every route but the stream route, `401` to a missing or wrong token, and checks `Host`. [builder's call] Why: one streaming implementation, already tested for ranges, permits and stalls.
6. **Gateway relay:** when the remote target sends a gateway credential (`LoginMethod::GatewayKey`, `LoginMethod::GatewayBasic`, or a configured `gateway_key_header`), the TUI starts a loopback relay (`127.0.0.1:0`, path `/relay/<token>`, same token rules as decision 2, at most 16 tokens and 8 requests at once) that forwards `GET`/`HEAD` and one `Range` header to the server's stream URL with the gateway headers added. [builder's call] Why: a gateway checks `Authorization` (or its key header) before the server sees the URL token, and a media player cannot send headers; this is the only way those setups can stream. The owner may want to know: in these setups the player's URL is a loopback relay URL, not the server's.
7. **Which file `s` plays:** in the focused file list, the focused file; in the table, the largest non-pad file of the selected torrent (the backend picks it). [builder's call] Why: the common case is one video plus small extras.
8. **Player discovery:** `player.program` in `config.yaml`: `auto` (default), `mpv`, `vlc`, or a path or command name; `player.args` are extra arguments put before the media. `auto` tries mpv, then VLC: `PATH` first, then the platform's usual install paths. None found: notice `No media player found. Install mpv or VLC, or set player.program in config.yaml.` and nothing else happens. [builder's call] Why: mpv starts faster and handles HTTP seeking well; VLC is the common second choice.
9. **Probe:** one write of six queries (kitty graphics query, XTVERSION, iTerm2 `ReportCellSize`, `CSI 16 t`, `CSI 14 t`, DA1), read byte by byte with `rustix::event::poll` until the DA1 answer, at most 4096 bytes, deadline 300 ms; if reply bytes have started arriving by then, the deadline extends to 1 s total. Runs once, after the terminal is in raw mode and before `EventStream` exists. Skipped (text title) on Windows, when stdin is not a terminal, inside tmux or GNU screen (`TMUX` or `STY` set, or `TERM` starting `screen` or `tmux`), with `TERM=dumb`, and with `logo: off`. [builder's call] Why: every terminal answers DA1, so DA1 last ends the wait without a timeout in the common case; reading one byte at a time never takes a keystroke typed after the answer; Windows console input is not a byte stream crossterm leaves to us.
10. **Protocol choice:** kitty with Unicode placeholders when the kitty query answers `OK` and XTVERSION names `kitty(` 0.28 or later, or `ghostty`; iTerm2 when `ReportCellSize` answers or XTVERSION starts with `iTerm2` or `WezTerm`; sixel when DA1 lists `4`; otherwise none. [builder's call] Why: placeholders make the image ordinary cell text, which ratatui diffs like anything else; WezTerm's kitty support has no placeholders but its OSC 1337 is complete.
11. **No cell pixel size, no logo.** Cell size comes from `ReportCellSize` (iTerm2, points times its scale), else `CSI 16 t`, else `crossterm::terminal::window_size()` (the window-size ioctl), else `CSI 14 t` divided by the cell grid; values outside 2..=64 wide or 4..=128 tall are ignored. [builder's call] Why: an image the terminal has to scale is the blurry logo the owner ruled out.
12. **Where the logo goes:** the full view's header (3 rows, only when the header has 3 rows) at the left with the three text lines beside it; the help screen (`?`) at the top, 10 rows, or 8, or 6, whichever fits above the key list, else none. No splash screen and no logo in the minimal view. [builder's call] Why: startup is fast and a splash would only delay the table; spec 5.3 allows "splash, about or help".
13. **`logo: auto | off`** at the top level of `config.yaml`. [builder's call] Why: a way out for a terminal that misbehaves on the queries.

## Review Focus

1. A stream token opens exactly one file: another file's path, the event stream, any other route, a token past its first-use window, idle limit or 8-hour cap → `401`/`403`. Tests in Task 1 (`stream_token_rules`) and Task 3 (`stream_token_is_scoped_to_one_file`).
2. No credential on the player's command line: the fake player's recorded argv holds no `token=`, no password, no `Bearer`, and the playlist file is `0600` and gone after the player exits. Test in Task 5 (`player_args_hold_no_secret`).
3. A hostile server's stream answer (a path with `\n`, a `file://` URL, 2 KiB of path, garbage JSON) never reaches a playlist. Test in Task 4 (`hostile_stream_path_is_refused`).
4. The relay is bounded: a 300-byte `Range` is dropped, the ninth concurrent request gets `503`, an upstream that never answers its head gets `504` within the head timeout, and only whitelisted headers come back. Test in Task 4 (`relay_is_bounded`).
5. The probe never stalls: a terminal that never answers costs 300 ms; one that answers DA1 is read no further than DA1's final `c`. Tests in Task 8 (`probe_times_out`, `probe_stops_at_da1`).
6. Crispness: the prepared image is exactly `cols x cell width` by `rows x cell height` pixels (times iTerm2's scale), so no terminal scales it. Test in Task 7 (`logo_pixels_match_cells`).
7. No re-sending: the same placement across frames produces zero bytes after the first; a removed iTerm2 or sixel placement is repainted from the buffer. Tests in Task 9 (`placer_sends_once`, `placer_repaints_removed`).
8. The kitty row and column diacritics table matches kitty's `rowcolumn-diacritics.txt` (the controller checks the first 24 against the kitty graphics protocol documentation before Task 7 merges).

### Task 3: Server stream tokens

**Files:** Create `crates/fbtt-server/src/routes/stream.rs`; Modify `crates/fbtt-server/src/routes/mod.rs`, `crates/fbtt-server/src/auth/mod.rs`, `crates/fbtt-server/tests/server.rs`

**Interfaces:**
- Consumes: `fbtt_core::stream::{StreamTokens, stream_path}`, the session the server already holds, `FbttAuth`.
- Produces:
  - `POST /api/v1/stream-tokens` with `{ "torrent": "<40 or 64 hex>", "file": <usize> }` (body through the existing JSON extractor, so `max_body_bytes` applies) → `201 { "path": "/api/v1/torrents/<40 lowercase hex wire hash>/files/<index>/stream?token=<t>", "expires_in": 60 }`. ### Task 9: Placing the logo without flicker

**Files:** Create `crates/fbtt-tui/src/graphics/place.rs`; Modify `crates/fbtt-tui/src/view/{mod.rs,header.rs}`, `crates/fbtt-tui/src/modal/{mod.rs,help.rs}`, `crates/fbtt-tui/src/lib.rs`, `crates/featherbittorrent/src/{switch.rs,run.rs}`, `crates/fbtt-tui/tests/views.rs`

**The mechanism (decided):**
- **Kitty:** the image is transmitted once per id and size (`transmit` then `place` with `U=1`, a virtual placement), and the view writes placeholder cells (`placeholder(row, col)`, foreground `id_colour(id)`) into the ratatui buffer. They are ordinary text, so ratatui's diff redraws them only when they change and a screen clear does not lose the image. On a new cell size the image is transmitted again under the same id. On exit, `delete` for both ids before the terminal is restored.
- **iTerm2 and sixel:** the view marks the logo's cells `Cell::set_skip(true)` (ratatui's crossterm backend never writes a skipped cell), and after `terminal.draw` returns, the `Placer` writes the image at that rect wrapped in `ESC 7`, `ESC [ <y+1> ; <x+1> H`, payload, `ESC 8`, only when the placement is new: different rect, different image, or the screen size changed since the last frame (ratatui cleared it). A placement that disappears (a dialog opened over it, the help screen closed) is repainted from the drawn buffer's own cells, because ratatui's diff would skip cells that did not change in its eyes and leave the image on screen.
- **Overlap:** logos are applied last in `draw_with`, after any modal; a logo rect that intersects the open modal's rect is not placed that frame.

**Interfaces:**
- `graphics::mod.rs`: `pub enum LogoSize { Small, Large(u16 /* rows */) }`; `pub struct PreparedLogos { pub graphics: Graphics, pub small: Option<Prepared>, pub large: Vec<Prepared> /* 10, 8, 6 rows */ }`, `pub struct Prepared { pub size: LogoSize, pub dims: LogoDims, pub payload: Arc<[u8]> /* kitty: transmit+place; iTerm2: inline; sixel: encoded */ }`; `pub fn prepare(graphics: Graphics) -> PreparedLogos` (CPU work, called on the blocking pool); `pub struct LogoView<'a> { pub logos: Option<&'a PreparedLogos> }` with `LogoView::text()`.
- `view::draw_with(frame: &mut Frame, model: &Model, snap: &Snapshot, logos: LogoView<'_>) -> Vec<Placement>`; `view::draw` stays and calls it with `LogoView::text()`, so every existing test is unchanged. `pub struct Placement { pub size: LogoSize, pub rect: Rect }`.
- Header: with a small logo and a header 3 rows tall, the logo takes `dims.cols` columns at the left plus one blank column, and the three lines draw in the rest; otherwise exactly today's output.
- Help: with a large logo that fits (`modal::help` gets the rows left after the key list), the logo is centred at the top of the help box above the keys.
- `place::Placer`: `Placer::new(protocol: Protocol)`, `before_draw(&mut self, logos: &PreparedLogos) -> Vec<u8>` (kitty: the payloads not yet sent for this cell size; others: empty), `after_draw(&mut self, placements: &[Placement], screen: Size, logos: &PreparedLogos) -> AfterDraw` with `pub struct AfterDraw { pub repaint: Vec<Rect>, pub bytes: Vec<u8> }`, `invalidate(&mut self)`, `on_exit(&self) -> Vec<u8>`.
- Binary: after `detect`, `prepare` runs on `spawn_blocking`; until it answers, the screen draws with `LogoView::text()`. Each frame: `before_draw` bytes written to `terminal.backend_mut()`; `let done = terminal.draw(|f| placements = view::draw_with(..))?`; copy the cells of `after.repaint` rects out of `done.buffer`; then `terminal.backend_mut().draw(cells)`, then `after.bytes`, then flush. On `Event::Resize`, `crossterm::terminal::window_size()`: a changed non-zero cell size prepares again on the blocking pool; the `Placer` is invalidated. Before the terminal is restored, `on_exit` bytes are written.
